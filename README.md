# Duck Lab

以项目为主线的机器人学习与实验记录工作台，当前聚焦 MicroDuck 复刻。个人可以独立使用，也支持多位成员共享任务、记录和讨论。

**纯静态网站，无数据库，无第三方前端依赖。** 网站和起步计划存放在仓库；真实进展、实验、想法、求助和任务讨论存放在 GitHub Issues。第一版不在网站内收集账号、密码或令牌，提交、评论和表情回应使用 GitHub 自身的登录。

## 先在本地看

需要 Node.js 20 或更新版本，无需运行 npm install。

```sh
npm run dev
```

打开 http://127.0.0.1:4173 。不要直接双击 index.html，浏览器不能从 file:// 读取配置文件。

```sh
npm test
npm run build
```

构建结果在 dist/，支持个人站点和 /仓库名/ 项目子路径。

## 发布到 GitHub Pages

1. 建议新建一个专门的公开仓库，例如 duck-lab，把本目录中的所有源文件上传到仓库根目录。保留 .github/ 隐藏目录；不必上传 dist/。
2. 修改 config.json：填写 owner、repo、成员称呼和 GitHub 用户名。`members` 数组最多支持 8 位成员；用户名用于匹配 Issue 的负责人，网站不会因此获得你的账号权限。
3. 主分支使用 main。在仓库 Settings → Pages → Build and deployment 中，将 Source 设置为 GitHub Actions。
4. 推送 main，或在 Actions 中手动运行 Deploy learning space。工作流会运行测试、构建和部署。部署后的真实地址显示在 Pages 设置和该工作流结果中。
5. 在仓库 Settings → General 中启用 Issues。需要协作时邀请其他成员，让参与者能够编辑任务标签、关闭任务和提交资料。此步骤由仓库所有者在 GitHub 操作。
6. 可选：在 Actions 手动运行 Setup issue labels，创建任务状态和内容类型标签。它只新增或更新本项目标签，不删除已有标签。

GitHub Pages 的可用性与仓库可见性有关；这份无登录读取方案以公开仓库和公开 Issues 为目标。不要上传准备保密的内容。私有仓库读取不属于此版本能力。

## 怎样使用

- 首页查看 MicroDuck 当前阶段、下一步、近期记录与协作状态。
- 看板点击任务，查看目标、主责、下一步、验收标准，再创建关联 Issue。
- “记录与讨论”把进展、实验、想法和求助放在一条项目时间线上。填写后到 GitHub 检查并提交；没有仓库时，可以下载 Markdown 草稿。
- “学习路径”同时展示当前阶段课程、MicroDuck 原始资料和机器人长期方向。课程只有在能支撑任务或阶段成果时才进入近期计划。
- 在 GitHub Issue 下评论、@其他成员或发送表情回应。网站显示回应数量并提供直达链接；不会假装在本地已经完成提交。
- 默认读取发布时的数据快照，日常浏览不消耗 GitHub 公开 API 额度。新增或修改 Issue、评论和标签会触发 Pages 重新构建，完成后刷新页面即可看到快照更新；“刷新最新”按钮可主动读取实时 API。
- 网站不会自动提交、自动通知或持续轮询。实时 API 限流或超时会保留可用快照；没有快照时明确回退到起步计划。
- 当前起步计划中的分工是建议，未虚构任何完成记录。

### 任务如何与看板关联

起步任务都有 T01—T10 编号。通过任务详情创建的 Issue 标题形如 `[任务] T01 确认硬件与软件版本`，网站按编号匹配。新任务没有编号时，会作为独立 GitHub 任务出现在看板。

| Issue 条件 | 看板状态 |
| --- | --- |
| 关闭 Issue | 完成 |
| doing 标签 | 进行中 |
| waiting 标签 | 等待 |
| ready 标签 | 准备好 |
| backlog 标签或无状态标签 | 待选 |

同一任务请复用一个 Issue；若出现重复，最近更新的 Issue 决定该任务状态。阶段和验收详情来自 data/space.json，更新起步任务时请同时维护该文件。Issue 分配给配置中识别出的 GitHub 用户后，看板会采用该负责人；未识别时保留计划分工。

类型通过标题前缀或标签识别：`[任务]`、`[进展]`、`[实验]`、`[想法]`、`[求助]`。专用仓库中没有识别标记的普通 Issue 会归入求助。Pull request 不计为学习记录。

## 内容存在哪里

| 内容 | 位置 |
| --- | --- |
| 空间名、仓库、成员 | config.json |
| 项目、四段路线、课程、起步任务、候选想法、资料 | data/space.json |
| 实际进展、实验、想法、求助、任务状态、评论和回应 | GitHub Issues |
| 代码、操作手册、较大的原始实验文件 | 仓库文件，或 Issue 中关联的外部资料 |

“工作台设置”保存在**当前浏览器**，便于先试用。要让成员共享设置，保存后下载当前 config.json，再提交到仓库根目录。它不是云同步；网站会明确说明。恢复仓库配置会清除当前路径的本机覆盖。

学习内容不要重复录入多个工具：Issue 保存原始过程，稳定的结论再整理成仓库文档。路线和计划不等于已学会，任务完成应附验收证据。

## 已实现与边界

- 四个一级页面：首页、任务、记录与讨论、学习路径；另有全局搜索、任务负责人和阶段筛选、阶段切换、任务详情。
- 五类记录编辑模板、Markdown 下载、GitHub 预填提交页。
- 无需令牌读取公开 Issues，处理分页、限流、超时与失败；最多读取最近更新的 300 条 API 记录，包含 PR 时实际 Issue 数量会更少。
- Pages 工作流使用 GitHub 自带的临时授权，在构建阶段生成公开 Issue 快照；该授权不会出现在网页。为防止误发布，快照仅从网站所在的同一个公开仓库生成，config.json 中应填写该仓库。
- 桌面与手机布局，键盘焦点、对话框与减少动画偏好。
- 不支持站内 GitHub OAuth、拖动写回看板、私有 Issue、即时聊天、站内附件上传、共享 agent。这些可在后续按实际需求增加。
- 网站显示的是转义后的文本预览，不执行 Issue 中的 HTML；文件与数据库中不保存访问令牌。

## 日常维护

建议每周一次短同步，展示成果、解阻塞、选下一步；每两周一次结对实验。记录包括版本、假设、结果、证据、下一步。每个里程碑结束，把零散记录整理为手册、报告或作品。

修改路线或课程后运行 npm test 和 npm run build。应用代码位于 app.mjs，样式位于 styles.css，GitHub 数据转换位于 lib/core.mjs。

## GitHub 账号需要提供什么

本地开发不需要账号。准备发布时提供公开 GitHub 用户名、希望使用的仓库名和成员称呼即可。仓库创建、邀请协作者、上传和发布需要使用你自己的 GitHub 登录授权；不要把密码或访问令牌发到聊天里。
